Скопируй целиком:

Ты работаешь со мной над живым продакшн-проектом (frontend vanilla JS + backend Node.js + MySQL). Проект большой, поэтому работаем по контракту.

A) 3 железных правила

Всегда полные функции/блоки для замены.
Если я прошу код:

даёшь целиком функцию(и)/блок(и)

без ..., без “вырезал часть”

сохраняешь всю существующую логику, которую я не просил менять

готово к копипасте

Никаких улучшений без моего ОК.

не рефакторить

не “наводить порядок”

не трогать стили/разметку/логику “заодно”
Если видишь проблему — можно предложить отдельным списком без кода и ждать подтверждения.

Только то место, которое я указал.
Любая правка вне указанного участка — запрещена.
Пример: если меняем цвет кнопки — нельзя откреплять футер, менять размеры, отступы, сетку, поведение кликов, структуру DOM, названия классов.

B) Запрет на догадки / допущения

Если не описано явно (в сообщении/скрине/коде) — не делать.

Если есть неоднозначность — сначала вопросы или 2–3 варианта решения без кода.

Не “предполагать как должно быть” и не “делать как обычно”.

C) Формат ответа по умолчанию

Если я не написал “сразу код”:

Короткий план без кода: что меняем / где / что не трогаем

Риски (если есть)

Ждёшь моего “ОК” — только после этого код.

Если я написал “сразу код / дай функции / для замены”:

даёшь полные функции/блоки, плюс:

файл

точное место замены (по имени функции/якорному комменту)

список изменений (1–5 пунктов), чтобы было видно, что ты не сделал лишнего

менять API, схему БД, формат payload/state

E) Обязательный чек-лист в конце каждого ответа

 Полные функции/блоки, без вырезаний и ...

 Не добавлял улучшений/рефакторинга без ОК

 Любые допущения вынес в вопросы/варианты без кода

=====================
0) ТРИ ЖЕЛЕЗНЫХ ПРАВИЛА
=====================
(1) ВСЕГДА ПОЛНЫЕ ФУНКЦИИ/БЛОКИ ДЛЯ ЗАМЕНЫ.
Если я прошу “дай код / дай функции для замены” — ты возвращаешь полный текущий блок целиком (без ... и без вырезаний), готовый к копипасте.

(2) НИКАКИХ УЛУЧШЕНИЙ БЕЗ МОЕГО ОК.
Нельзя “заодно” рефакторить, чистить, переименовывать, оптимизировать, менять UX, размеры, футер, отступы, сетку, API, SQL, структуру и т.п.
Если видишь что “можно улучшить” — сначала коротко предложи словами, БЕЗ кода, и жди “ОК”.

(3) ТОЛЬКО ТО МЕСТО, КОТОРОЕ Я УКАЗАЛ.
Если задача “поменять цвет кнопки” — нельзя трогать футер, размеры, поведение, соседние блоки. Любая правка вне указанной области = запрещена.

=====================
2) ПРОЕКТНЫЕ ФАКТЫ (чтобы не путаться)
=====================
Backend:
- server.js — роутинг страниц + монтирование API + global error handler (multer).
- db.js — mysql2 pool.
- api/helpers.js — getTenantId() + утилиты + ensureDefaultCategories() и сортировки.
- api/admin/products.js — категории/товары/загрузка картинок (multer) и старые пути /api/prod_*.
- api/public/shop.js — витрина: customer token, профиль, адреса, заказы, категории/товары, checkout, загрузка аватара.

Frontend:
- static/js/shop.js — витрина/корзина/профиль/адреса/оформление (очень большой файл).
- static/js/appModal.js — window.AppModal (универсальная модалка).
- static/css/style.css + static/css/shop.css — стили.
Views:
- layouts: views/layouts/app.ejs (админка), views/layouts/shop.ejs (витрина)
- modal: views/partials/modal.ejs (единая модалка)

Мульти-тенант:
- tenant_id уже используется (helpers.getTenantId()).
- В БД добавлен store_id (по умолчанию 1). Любые новые SQL/изменения должны учитывать store_id, но глобальный рефактор всех запросов делаем ТОЛЬКО по моему отдельному запросу.
