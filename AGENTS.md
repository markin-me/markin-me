1. Без регрессий.
2. Без выдуманных изменений.
3. Менять только оговорённое.
4. Остальное не трогать.
5. Если задача неясна — сначала уточнить, потом писать код.
6. Только минимальные точечные правки в пределах задачи.
7. Большие переписывания и массовые замены запрещены без явной необходимости и согласования.
8. Не трогать чужие изменения.
9. UTF-8 не ломать, кодировку существующих файлов не менять.
10. Не скрывать ошибки fallback’ами, хаками и заглушками.
11. Исправлять причину проблемы, а не симптомы.
12. UI-правки делать без лишних ререндеров и полных пересчётов.
13. Перед правкой коротко писать, что меняешь.
14. После правки коротко писать, что изменил и что не трогал.
15. Проверять только синтаксис и критичный сценарий.
16. Не списывать отсутствие изменений на кэш без прямых признаков.
17. Существующие модалки, overlay, sheets, popup-компоненты и их сценарии не дублировать.
18. Если модалка или её логика уже существуют, сначала расширять текущую реализацию через параметры, контекст открытия, существующий API или точечный вызов.
19. Создавать новую параллельную реализацию модалки, новый bridge, controller, service или другой дублирующий слой для уже существующей функциональности запрещено без явного согласования.
20. Перед созданием нового файла сначала изучить существующую структуру соответствующего модуля и проверить, нет ли уже подходящего файла, компонента, helper, hook, API-модуля, controller, service, adapter или другой точки расширения. Не создавать новый файл только потому, что так быстрее или проще обойти существующий код.
21. Новый файл разрешено создавать без отдельного согласования, если он является естественной частью уже существующей архитектуры и нужен для правильного разделения ответственности: новая самостоятельная страница/экран, новый переиспользуемый компонент, hook, helper, API-модуль, provider adapter, repository, domain-модуль или другой самостоятельный элемент, который по структуре проекта должен жить отдельно.
22. Минимальные правки не означают, что весь новый функционал нужно складывать в один существующий большой файл. Если добавление новой самостоятельной сущности в старый файл смешает разные ответственности, ухудшит структуру или создаст монолит, нужно создать логично расположенный отдельный файл в рамках уже существующей структуры проекта.
23. При создании новых файлов соблюдать существующие папки, naming conventions, границы модулей и направление зависимостей. Не создавать рядом вторую параллельную архитектуру, новые корневые каталоги, новые слои, bridge/controller/service-системы или собственные шаблоны структуры, если в проекте уже есть принятый способ организации аналогичного кода.
24. Если для задачи действительно требуется новый архитектурный слой, новый корневой каталог, новая параллельная подсистема, массовое разбиение/перенос существующих файлов или существенное изменение структуры проекта, сначала объяснить зачем это необходимо и дождаться подтверждения.
25. Не создавать файлы-заглушки, пустые абстракции и файлы «на будущее». Каждый новый файл должен иметь конкретную ответственность и реально использоваться текущей задачей.
26. Не дублировать код между новыми файлами. Общую логику выносить в переиспользуемый модуль только когда она действительно используется несколькими частями системы или является самостоятельной общей ответственностью; не делать абстракции ради абстракций.
27. Тесты не запускать и не выполнять — пользователь проверяет их самостоятельно.
28. Порт 3000 не занимать.
29. Для мобильных приложений iOS и Android создавать новые файлы логично и структурно: новые самостоятельные экраны и крупные независимые части не складывать в один общий файл только ради минимального количества файлов.
30. Для `mobile-apps/mobile-user` вести структуру страниц раздельно: каждая самостоятельная страница/экран должна находиться в своём логичном файле/папке (`catalog`, `product`, `combo`, `combo-replace` и т. д.). Общие карточки, компоненты, hooks, API, types и helpers выносить в переиспользуемые модули согласно существующей структуре. Не складывать разные страницы и разные ответственности в один большой файл.
31. При добавлении новой страницы в mobile-app сначала проверить существующую структуру навигации, соседние страницы и общие компоненты; новую страницу подключать через существующий navigation/router pattern, не создавать параллельную навигацию.
32. Для backend/service-кода придерживаться того же принципа: самостоятельный provider, adapter, repository, worker или domain-модуль может и должен быть отдельным файлом, если это соответствует существующей архитектуре. При этом запрещено создавать дублирующий service/controller/repository, если аналогичная ответственность уже существует и её можно корректно расширить.
