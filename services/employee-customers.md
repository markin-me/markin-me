# Карточка покупателя сотрудника

## Модель и границы

Переиспользуется `cust_customers` из main, включая заказы, адреса, бонусы,
скидки и `cust_customer_sessions`. Новая таблица не является вторым справочником
покупателей: `auth_employee_customer_links` хранит только отношение к `app_users`,
доказанный телефон и код конфликта.

`PRIMARY KEY (tenant_id, employee_id)` обеспечивает одну связь сотрудника.
`UNIQUE (tenant_id, customer_id)` не позволяет двум сотрудникам присвоить одну
карточку. Составные FK с tenant в обе стороны запрещают межмагазинные связи;
`ON DELETE RESTRICT` защищает покупателя и историческую связь. Увольнение выполняется
существующим архивированием сотрудника, а не удалением покупателя.

`ensureEmployeeCustomer` вызывается в транзакциях создания сотрудника, регистрации
владельца и сохранения сотрудника, а также при подтверждении служебного мессенджера.
Tenant блокируется `FOR UPDATE`; повторный вызов возвращает существующую связь.
Ошибка создания карточки/отношения приводит к откату родительской транзакции.
Телефон из формы сотрудника не копируется в покупателя. Неизвестный телефон — NULL,
никогда не фиктивный номер и не пустая строка.

Уже существующая карточка может быть выбрана при первоначальном создании отношения
только при общем подтверждённом канале сотрудника и покупателя, общей person identity,
одном tenant, активном покупателе и отсутствии связи с другим сотрудником.
Совпадение телефона не является доказательством. Несколько подтверждённых кандидатов
создают отдельную NULL-карточку и конфликт. Исторические карточки автоматически
не сливаются, не удаляются и не перепривязываются после создания отношения.
Если подходящая старая карточка обнаружена позднее, требуется разбор администратором:
автоматического переноса заказов, адресов и сессий нет.

## Подтверждение и права

После привязки мессенджера через авторизованную CRM-сессию связанная карточка получает
тот же подтверждённый канал, если нет конфликтов legacy ID и person identity.
Служебная и клиентская записи в `auth_account_links` остаются раздельными.
Customer JWT/сессии не заменяются сотрудническим JWT. Роли не копируются в покупателя.

Телефон Telegram обрабатывается только внутри защищённого tenant webhook:
личный чат, не bot sender, `contact.user_id == from.id == chat.id`, нормализация.
Сотрудник ищется только через уже подтверждённую служебную messenger-привязку,
не по телефонному номеру. Чужой контакт и контакт без user_id отклоняются.
MAX-привязка поддерживается; подтверждение MAX-телефона не добавлено, поскольку
достоверность contact-события используемого MAX API не подтверждена.

Конфликт сохраняется в отношении, не присваивает историю чужого покупателя и не
повышает права. При конфликте подтверждённый телефон остаётся в отношении для
разбора, но не записывается поверх чужого/спорного номера клиента.
Администратор с `team.employees.read` читает статусы через
`GET /api/admin/team/employee-customers`. Само разрешение конфликтов и перенос данных
не выполняются автоматически; отдельного UI слияния не создано.

## NULL и клиентские сценарии

Просмотрены основные потребители: `api/public/shop.js`, `api/admin/clients.js`,
`api/telegramNotifications.js`, `api/printPush.js`, `static/js/clients.js`,
`static/js/new-order.js`, `static/js/shop-late.js` и соответствующая клиентская модель main.
Отображение использует nullable-safe преобразования; поиск LIKE не считает NULL
совпадением. Создание покупателя через обычную форму и вход по телефону сохраняют
существующие проверки номера. Права на бонусы и акции остаются правилами магазина.

В оформлении заказа с обязательными клиентскими данными добавлен запрет для
авторизованного покупателя с NULL-телефоном: `PHONE_VERIFICATION_REQUIRED` с подсказкой
заполнить и подтвердить телефон. Гостевые правила и необязательные клиентские данные
не изменены. Связь сотрудника не является подтверждением телефона.
Импорт и другие прямые SQL-записи должны передавать NULL вместо пустой строки;
CHECK и существующие unique индексы отклоняют неканонические и повторные номера.
Полный импорт и оплаченные реальные заказы не запускались.

Общая новая code-auth использует 4 цифры с ведущими нулями, криптографическую генерацию,
TTL 3 минуты и прежние ограничения попыток/запросов. UI CRM и витрины согласован с
форматом. Существующие сессии и auth_version не изменяются. Во время выкладки старые
6-значные challenge не пройдут новую проверку: нужно дать им истечь до обновления
или запросить новый код, не менять пользовательские сессии.

## Миграция: подготовлена, НЕ применена

`migrations/011-employee-customers.js` соответствует существующим JS-миграциям проекта.
Применение разрешено только к `a1186497_test`, после отдельного подтверждения.
Перед DDL проверяются DATABASE(), тип phone, каноничность телефонов, нормализованные
дубли, tenant-composite и phone unique ключи. Существующие телефоны не переписываются.
При несовместимости выполнение прекращается до изменения phone.

План после разрешения:

1. Остановить запись на время согласованного окна, не затрагивая другие среды.
2. Сделать проектным/серверным средством согласованную резервную копию структуры и
   данных `app_users`, `cust_customers` и зависимых таблиц; проверить восстановление
   на изолированной копии. Команда резервирования здесь автоматически не запускается.
3. Подтвердить MySQL >= 8.0.16 (enforced CHECK), InnoDB, FK-типы INT и свободное место.
4. Выполнить миграцию: phone nullable, канонический CHECK, таблица отношений.
   DDL MySQL не транзакционен: после ошибки сначала проверить фактическую схему,
   не считать rollback транзакции откатом ALTER TABLE.
5. Выполнить предварительный просмотр: `node scripts/backfill-employee-customers.js --tenant=1`.
6. После просмотра и разрешения: та же команда с `--apply`. Весь tenant — одна
   транзакция; повторный запуск не создаёт повторных связей. Каждый tenant выбирается явно.
7. До открытия записи сверить отсутствие сотрудников без связи и межмагазинных FK,
   проверить отсутствие изменений заказов, адресов, ролей и сессий.

Реально выполненный read-only preflight: MySQL 8.0.37-29, неканонических номеров 0,
нормализованных дублей 0. Это не заменяет свежую проверку сервера перед миграцией.
Предварительный просмотр до миграции обнаружил 5 сотрудников tenant 1 без новой
явной связи. Заполнение не выполнялось. Скрипт preview не раскрывает личные данные.

## Откат

До первой записи NULL-карточек возможен согласованный возврат старого кода и NOT NULL
после проверки `COUNT(*) WHERE phone IS NULL = 0`. После появления таких карточек
автоматический обратный ALTER запрещён. Не удалять карточки/связи ради отката и не
откатывать всю БД поверх новых заказов. Предпочтителен forward fix с сохранением
nullable-схемы; старый код можно возвращать только после проверки его NULL-совместимости.
Резервная копия для аварийного восстановления применяется только в согласованном
окне с учётом новых записей. Разрушительного down-script нет.

## Проверки и готовность

Синтаксические проверки и адресная диагностика с искусственной БД:
создание NULL-карточки, повторное сохранение без дубля, откат при ошибке связи,
отклонение чужого tenant и недостоверных контактов. Тестовые наборы не запускались.
В Chrome отрисована существующая CRM-страница входа на 375/768/1440 px: поле
подтверждения принимает 4 символа, placeholder 0000, горизонтального переполнения нет.
Проверены ведущие нули и отклонение шестизначного ввода до обращения к БД.
Фактическая миграция, backfill и real-bot end-to-end не выполнялись. До миграции
этот код создания сотрудников нельзя выкладывать: отсутствие таблицы должно явно
прерывать операцию, а не создавать сотрудника без покупателя.
